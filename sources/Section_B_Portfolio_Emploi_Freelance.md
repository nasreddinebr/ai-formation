### Écrire des Articles Techniques : Pourquoi et Comment

**🔑 Intuition — enseigner pour démontrer sa compréhension**

Rappelle-toi le Module 1, chapitre 1 (méthode d'apprentissage) : "Enseigner" (10% de la méthode Learn-Build-Teach) est l'étape qui révèle si une notion est réellement comprise, ou seulement vaguement saisie. Écrire un article technique applique exactement ce même principe, mais **publiquement** : expliquer un concept avec ses propres mots, pour un public qui ne l'a jamais rencontré, oblige à une clarté que la simple utilisation d'un outil ne requiert pas.

```
🔑 Ce qui fait un bon article technique (pas juste un résumé de doc) :

- Partir d'un PROBLÈME CONCRET rencontré (pas une notion abstraite)
- Expliquer le RAISONNEMENT, pas seulement la solution finale
  (rappel : exactement la pédagogie "Explication avant Code"
  utilisée dans toute cette formation)
- Inclure du CODE FONCTIONNEL et testé, pas des extraits approximatifs
```

**💡 Le bénéfice à double sens :** au-delà de la visibilité externe, rédiger un article technique force souvent à **découvrir des lacunes** dans sa propre compréhension d'un sujet qu'on pensait pourtant maîtriser — un effet secondaire précieux, indépendant de la publication elle-même.

### Contribuer à l'Open-Source : Commencer Petit

**🔑 Intuition — rappel direct du Module 1 (Git/GitHub) et du Module 8 (LangChain)**

Contribuer à un grand projet open-source (comme LangChain, Module 8, ou Hugging Face Transformers, Module 5) peut sembler intimidant. Mais la plupart des mainteneurs accueillent favorablement de **petites contributions bien ciblées**, un excellent point d'entrée :

```
🔑 Contributions accessibles pour commencer :

- Corriger une erreur dans la DOCUMENTATION (rappel : lire du
  code existant, comprendre son fonctionnement, sans avoir à
  concevoir de nouvelle fonctionnalité complexe)
- Signaler un BUG précisément reproduit, avec un exemple minimal
  (rappel Module 1 : isoler un problème méthodiquement)
- Ajouter un TEST manquant pour une fonctionnalité existante
  (rappel Module 9, chapitre 9.4 : les tests de code)
```

**💡 Pourquoi c'est valorisé par les recruteurs :** une contribution acceptée, même petite, démontre que tu sais **lire et comprendre le code d'autres personnes** (une compétence différente d'écrire son propre code from scratch), et que tu respectes les conventions et processus d'une équipe déjà établie — des compétences directement transférables à un environnement professionnel en entreprise.

### Qu'est-ce que Kaggle, et Pourquoi C'est Valorisé

**🔑 Intuition**

Kaggle est une plateforme où des entreprises et organisations publient de **vrais problèmes de Machine Learning**, avec un vrai dataset, invitant la communauté mondiale à proposer les meilleurs modèles possibles — souvent avec des prix en argent pour les meilleurs classements, mais surtout une **preuve publique et comparable** de compétence.

**💡 Pourquoi c'est spécifiquement valorisé par les recruteurs :** contrairement à un projet personnel (rappel Module 10.6), où l'on choisit soi-même le problème et les critères de réussite, Kaggle impose un **classement objectif et comparatif** face à des milliers d'autres participants, sur un problème et une métrique fixés à l'avance (rappel Module 3, chapitre 3.6) — une validation externe difficile à obtenir autrement.

---

### La Méthodologie du Module 3, Appliquée en Contexte Compétitif

**🔑 Intuition — rien de nouveau techniquement, mais une discipline renforcée**

Rappelle-toi l'intégralité du Module 3 : EDA, feature engineering, validation croisée, comparaison de modèles. Kaggle applique **exactement** cette même méthodologie, mais avec une contrainte supplémentaire cruciale : un **leaderboard public** qui révèle immédiatement si ta méthodologie est réellement rigoureuse, ou si elle contient des failles (comme une fuite de données, rappel Module 3, chapitre 3.1) qui te feraient sur-performer artificiellement sur tes propres tests, mais échouer sur le vrai jeu de test final caché.

```
🔑 Rappel Module 3, chapitre 3.1 : Train/Validation/Test

Sur Kaggle, cette discipline devient encore plus critique :
- Le "Public Leaderboard" utilise une PORTION du jeu de test
- Le "Private Leaderboard" (révélé SEULEMENT à la fin de la
  compétition) utilise l'AUTRE portion

🔑 Un piège classique : sur-optimiser son modèle pour bien
   performer sur le Public Leaderboard (en ajustant frénétiquement
   les hyperparamètres selon ce retour visible), au risque de
   surapprendre CETTE portion spécifique du test — exactement
   le piège de l'exercice 3.1.A du Module 3 (utiliser l'ensemble
   de test pour faire des choix), mais à l'échelle d'une compétition
```

---


## 💻 MISE EN PRATIQUE

```python
import pandas as pd
from sklearn.model_selection import KFold, cross_val_score
from sklearn.ensemble import RandomForestClassifier

# ─────────────────────────────────────────────
# 1. WORKFLOW TYPE D'UNE SOUMISSION KAGGLE (rappel intégral du Module 3)
# ─────────────────────────────────────────────

# ÉTAPE 1 : Charger les données (rappel Module 1)
train = pd.read_csv("train.csv")
test = pd.read_csv("test.csv")   # rappel : PAS de labels dans ce fichier !

# ÉTAPE 2 : EDA (rappel Module 1, 3)
print(train.describe())
print(train.isnull().sum())

# ÉTAPE 3 : Feature Engineering (rappel Module 3, chapitre 3.7)
def preparer_features(df):
    df = df.copy()
    df["FamilleSize"] = df["SibSp"] + df["Parch"] + 1
    df["Age"] = df["Age"].fillna(df["Age"].median())
    return df

train_prepare = preparer_features(train)
test_prepare = preparer_features(test)

# ÉTAPE 4 : Validation croisée RIGOUREUSE (rappel Module 3, chapitre 3.1)
X = train_prepare[["Age", "FamilleSize", "Pclass"]]
y = train_prepare["Survived"]

modele = RandomForestClassifier(n_estimators=200, random_state=42)
cv = KFold(n_splits=5, shuffle=True, random_state=42)
scores = cross_val_score(modele, X, y, cv=cv, scoring="accuracy")
print(f"\nScore CV (mon estimation FIABLE, pas le leaderboard) : "
      f"{scores.mean():.4f} ± {scores.std():.4f}")

# ÉTAPE 5 : Entraîner sur TOUTES les données train, prédire sur test
modele.fit(X, y)
predictions = modele.predict(test_prepare[["Age", "FamilleSize", "Pclass"]])

# ÉTAPE 6 : Créer le fichier de soumission au format EXACT attendu par Kaggle
soumission = pd.DataFrame({
    "PassengerId": test_prepare["PassengerId"],
    "Survived": predictions
})
soumission.to_csv("soumission.csv", index=False)
print("\n✅ Fichier de soumission prêt")

# ─────────────────────────────────────────────
# 2. ÉVITER LE PIÈGE DU SUR-AJUSTEMENT AU PUBLIC LEADERBOARD
# ─────────────────────────────────────────────

print("\n⚠️  Rappel Module 3, chapitre 3.1 :")
print("   Fais TOUJOURS confiance à ton score de validation croisée")
print("   (calculé ci-dessus) plutôt qu'au seul score du Public Leaderboard")
print("   pour choisir entre plusieurs modèles — le leaderboard public")
print("   n'est qu'UNE portion du vrai jeu de test final.")
```

### Exercice B.2.A — Public vs Private Leaderboard

Explique la différence entre le Public Leaderboard et le Private Leaderboard sur Kaggle, et pourquoi cette distinction reproduit un principe déjà vu au Module 3.

<details>
<summary>👉 Solution</summary>

Le Public Leaderboard affiche un score calculé sur **une portion** du jeu de test, visible en temps réel pendant la compétition ; le Private Leaderboard, révélé seulement à la fin, utilise **l'autre portion**, jusqu'alors totalement cachée aux participants. Cette distinction reproduit directement le principe du Module 3, chapitre 3.1 : le Public Leaderboard joue un rôle similaire à un ensemble de **validation** (qu'on peut consulter pour ajuster ses choix), tandis que le Private Leaderboard joue le rôle de l'ensemble de **test final**, qui ne doit influencer aucun choix avant son dévoilement — un participant qui sur-optimiserait excessivement pour le Public Leaderboard risquerait de surapprendre cette portion spécifique, et de chuter au classement final une fois le Private Leaderboard révélé.
</details>

### Exercice B.2.B — Pourquoi faire confiance à la validation croisée plutôt qu'au leaderboard

Un participant Kaggle constate qu'un modèle A obtient un meilleur score sur le Public Leaderboard qu'un modèle B, mais que le modèle B a un meilleur score de validation croisée (5-fold) sur ses propres données d'entraînement. Lequel des deux modèles devrait-il choisir pour sa soumission finale, et pourquoi ?

<details>
<summary>👉 Solution</summary>

Il devrait généralement **privilégier le modèle B**, celui avec le meilleur score de validation croisée. Rappelle-toi le Module 3, chapitre 3.1 : la validation croisée à 5 plis offre une estimation **beaucoup plus robuste et fiable** de la performance réelle d'un modèle, en moyennant sur 5 découpages différents des données, que le score du Public Leaderboard, qui n'est calculé que sur une **seule portion fixe et limitée** du jeu de test — un score potentiellement trompeur s'il résulte en partie du hasard sur cette portion spécifique. Se fier excessivement au score du Public Leaderboard pour choisir entre deux modèles est précisément le piège de sur-ajustement évoqué dans ce chapitre.
</details>

```python
mots_cles_par_metier = {
    "ML Engineer": ["MLflow", "Docker", "CI/CD", "monitoring", "scaling", "kubernetes"],
    "AI/LLM Engineer": ["LangChain", "RAG", "prompt engineering", "agents", "fine-tuning", "LLM"],

}

def decoder_offre_emploi(texte_offre):
    """Identifie le métier réel derrière une offre, selon ses mots-clés (rappel Module 10.5)."""
    texte_lower = texte_offre.lower()
    scores = {}
    for metier, mots_cles in mots_cles_par_metier.items():
        score = sum(1 for mot in mots_cles if mot.lower() in texte_lower)
        if score > 0:
            scores[metier] = score
    
    if not scores:
        return "Métier non identifiable clairement à partir de ces mots-clés"
    
    metier_probable = max(scores, key=scores.get)
    return f"{metier_probable} (score de correspondance: {scores[metier_probable]})"

sur nos données propriétaires.

print(f"Métier réel décodé : {decoder_offre_emploi(offre_test)}")
```

### Les Trois Types d'Entretiens Techniques IA

**🔑 Intuition**

Un processus de recrutement IA combine généralement plusieurs formats d'entretien distincts, chacun évaluant une dimension différente de tes compétences :

```
🔑 ENTRETIEN DE CODING (souvent en live, avec partage d'écran) :
   → Évalue tes compétences Python fondamentales (rappel Module 1)
   → Exercices typiques : manipulation de données (rappel Module 1,
     chapitre 1.3, Pandas), implémentation d'un algorithme simple
     from scratch (rappel Module 2 : régression linéaire, ou
     Module 4 : un neurone simple)

🔑 ENTRETIEN DE THÉORIE ML/DL :
   → Évalue ta COMPRÉHENSION des concepts, pas seulement ta
     capacité à utiliser des bibliothèques
   → Questions typiques : "Explique le compromis biais-variance"
     (rappel Module 3, chapitre 3.1), "Comment fonctionne
     l'attention dans un Transformer ?" (rappel Module 5, chapitre 5.3)

🔑 ENTRETIEN DE SYSTEM DESIGN IA :
   → Évalue ta capacité à concevoir un SYSTÈME COMPLET, pas
     seulement un modèle isolé
   → Questions typiques : "Comment concevrais-tu un système de
     recommandation à grande échelle ?" (mobilisant Module 3,
     Module 9, potentiellement Module 10, chapitre 10.1)
```

**💡 Pourquoi cette diversité de formats :** rappelle-toi le Module 10, chapitre 10.5 : les hard skills seules ne suffisent pas — un bon ingénieur IA doit à la fois savoir **coder** (entretien coding), **comprendre en profondeur** ce qu'il utilise (entretien théorique), et **concevoir des systèmes complets** (entretien system design), trois dimensions distinctes que les recruteurs cherchent à évaluer séparément.

### Calculer son Taux Journalier Moyen (TJM)

**🔑 Intuition — un calcul rarement fait correctement par les débutants**

Un freelance débutant fixe souvent son tarif "au hasard", ou en copiant simplement une fourchette vue en ligne, sans calcul rigoureux. Voici la logique à suivre :

```
🔑 Étape 1 : Estimer le revenu ANNUEL NET souhaité
   (équivalent à un salaire confortable pour ton niveau d'expérience)

🔑 Étape 2 : Estimer le nombre de JOURS RÉELLEMENT FACTURABLES
   par an — rappel : PAS 365 jours ! Il faut soustraire les
   weekends, congés, ET le temps passé en prospection commerciale,
   administratif, formation continue (rappel Module 10, chapitre
   10.5 : la veille technologique prend du temps, non facturable
   directement)

🔑 Étape 3 : Diviser le revenu souhaité par les jours facturables
```

**🧮 Exemple calculé**

```
Revenu annuel net souhaité : 50 000€

Jours ouvrés dans l'année : ~230
Moins : congés, prospection, administratif (souvent 30-40% du temps
        pour un freelance débutant) : -80 jours
Jours RÉELLEMENT facturables : 150 jours

TJM nécessaire = 50 000€ / 150 jours ≈ 333€/jour
```

**💡 L'erreur fréquente à éviter :** fixer un TJM en supposant, à tort, que 100% des jours ouvrés seront facturés — un calcul qui mène systématiquement à sous-évaluer son tarif réel nécessaire, et donc à travailler significativement plus que prévu pour atteindre le revenu visé.

```python
def calculer_tjm(revenu_annuel_souhaite, jours_ouvres=230, taux_non_facturable=0.35):
    """taux_non_facturable : proportion du temps NON directement facturée
    (congés, prospection, administratif, veille — rappel Module 10.5)"""
    jours_facturables = jours_ouvres * (1 - taux_non_facturable)
    tjm_necessaire = revenu_annuel_souhaite / jours_facturables
    
    print(f"Revenu annuel souhaité : {revenu_annuel_souhaite:,}€")
    print(f"Jours facturables estimés : {jours_facturables:.0f} jours")
    print(f"TJM nécessaire : {tjm_necessaire:.0f}€/jour")
    return tjm_necessaire

calculer_tjm(revenu_annuel_souhaite=50000)

# Comparer plusieurs scénarios d'expérience (rappel tableau du fichier de base)
print("\n--- Comparaison selon le service proposé ---")
for revenu_vise in [45000, 70000, 100000]:
    print(f"\nPour viser {revenu_vise:,}€/an :")
    calculer_tjm(revenu_vise)

verifier_checklist(checklist_contrat_freelance)
```
