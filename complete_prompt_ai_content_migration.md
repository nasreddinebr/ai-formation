The entire mission must be performed methodically: analyze the project first, propose the required changes, then implement them after the appropriate approval steps.

The final objective is to replace the old module and chapter content with the new, more complete and pedagogically improved content, while significantly modernizing the overall visual experience of the project.

# 15. Stable Content Mapping Strategy

The migration must use a **stable, explicit and deterministic mapping strategy** between application modules/sections and their source files.

Do not make a module's technical identity depend solely on:

* its title;
* its filename;
* a dynamically generated slug;
* its position in a list.

Prefer a stable identifier.

For example:

```text
module-01
module-02
module-03
...
module-10

section-a
section-b
section-c
```

These identifiers are illustrative only.

**First analyze the existing project conventions and reuse existing stable identifiers when they are reliable.**

Conceptually, the mapping should follow:

```text
Stable ID
→ source file
→ title
→ metadata
→ content
```

---

# 16. Single Source of Truth for Mapping

Avoid duplicating mappings in multiple places.

There should be one clearly identifiable source of truth.

Different parts of the application should consume this mapping instead of rebuilding their own mappings.

Avoid:

* approximate matching;
* partial string matching;
* title-based matching;
* array-position dependency;
* "smart" fallbacks;
* fragile inference.

If the mapping is invalid, the system should explicitly report the problem rather than silently selecting another file.

---

# 17. URL Stability

Changing a title or source filename must not unnecessarily change the technical identity or URL of a module.

If existing URLs depend on slugs or identifiers:

* preserve them whenever possible;
* do not change them without a real reason;
* analyze SEO consequences;
* implement redirects if genuinely required.
